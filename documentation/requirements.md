# CampusCare — Functional and Non-Functional Requirements Specification

**Project Title:** CampusCare – Smart Campus Complaint & Maintenance Management System  
**Document Purpose:** Academic Deliverable 1 (Software Design & Development Innovative Assessment)  
**Scope:** Academic Functional Prototype (HTML5, CSS3, Vanilla JavaScript, Browser LocalStorage)

---

## 1. Functional Requirements (FR1–FR7)

| ID | Requirement Title | Specification | Verification / Acceptance Criteria |
| :--- | :--- | :--- | :--- |
| **FR1** | **Role-Based Demo Authentication** | The system shall provide a demonstration login portal allowing users to select one of three roles (**Student**, **Administrator**, or **Maintenance Staff**) and choose a fictional demo profile without real passwords or backend verification, routing the user to the corresponding role workspace. | Selecting each role card populates role-appropriate demo accounts, displays sample login instructions, creates a session in `LocalStorage`, and opens only the authorized dashboard for that role. |
| **FR2** | **Validated Complaint Submission & Unique ID Generation** | Authenticated Students shall submit complaints via a dedicated form containing a required Title (min. 5 characters), required Category (`Electrical`, `Water Supply`, `Classroom Maintenance`, `Wi-Fi/Internet`, `Cleanliness`, `Other`), optional Location, required Description (min. 15 characters, max. 600), and optional image attachment (`PNG`, `JPG`, `WEBP`, max. 500 KB). On valid submission, the system shall generate a unique ID (`CMP-YYYY-XXXX`), record timestamps, and save the complaint with status `Pending`. | Submitting empty/short fields displays inline field errors and blocks submission; oversized (>500 KB) or non-image files are rejected; valid submission generates a unique sequential ID (`CMP-2026-1009`, etc.) and adds an initial audit history entry. |
| **FR3** | **Student Personal Dashboard & Complaint Tracking** | Authenticated Students shall view personal statistics (**Total**, **Pending**, **In Progress**, **Resolved**), category distribution, recent updates, and searchable/filterable complaint history. Students shall inspect full details including the four-stage status pipeline, assigned staff name, resolution notes, attached photo, and audit timeline. | Student dashboard displays metrics calculated strictly from the signed-in student's complaints; search and category/status filters update the list live; opening any personal complaint displays assigned staff and resolution notes when present. |
| **FR4** | **Administrator Triage, Prioritization & Assignment** | Authenticated Administrators shall view campus-wide statistics, category breakdowns, recent complaints, and the full complaint registry with search and filters (Category, Status, Priority). Administrators shall set Priority (`Low`, `Medium`, `High`, `Urgent`), assign complaints to Maintenance Staff, update workflow status, add notes, and delete records after modal confirmation. | Admin table lists all submitted complaints across all students; assigning a staff member to a `Pending` complaint transitions it to `Assigned` and logs the change in history; deleting a record prompts a confirmation dialog before removal. |
| **FR5** | **Maintenance Staff Task Queue & Resolution Workflow** | Authenticated Maintenance Staff shall view assigned task metrics and filterable task queues (**Active Assigned Tasks**, **Completed Tasks**, **All My Tasks**). Staff shall advance assigned complaints from `Assigned` to `In Progress` and mark tasks `Resolved` after entering mandatory resolution notes (min. 8 characters). | Clicking **Start Work (In Progress)** updates status immediately; attempting to save `Resolved` without >= 8 characters of resolution notes triggers an inline validation error; resolved complaints move to **Completed Tasks** and become visible to the Student and Admin. |
| **FR6** | **Role-Based Access & Data Isolation** | The system shall enforce role permissions on both screen navigation and record operations: Students shall only view/manage their own submissions and access Student screens; Maintenance Staff shall only view and update complaints assigned directly to their staff ID; Administrators shall manage campus-wide triage without modifying Student identity ownership. | Attempting to navigate to unauthorized screens or inspect unassigned/peer complaints is blocked with an **Access Denied** notification; Staff dashboards exclude unassigned and peer-assigned tickets. |
| **FR7** | **Persistent LocalStorage & Demo Data Reset** | The system shall persist complaint records, unique ID counter state, and active demo sessions in browser `LocalStorage` across page reloads, and provide a confirmation-guarded **Reset Demo Data** action to restore the default fictional dataset. | Submitting or updating a complaint and refreshing the browser retains all updated fields, status, notes, and active session; confirming **Reset Demo Data** restores the 8 baseline sample complaints. |

## 2. Non-Functional Requirements (NFR1–NFR3)

| ID | Requirement Title | Specification | Verification / Acceptance Criteria |
| :--- | :--- | :--- | :--- |
| **NFR1** | **Client-Side Security & Data Integrity** | The system shall escape all user-generated text before rendering into HTML to prevent XSS injection, validate image MIME types and size boundaries, and wrap `LocalStorage` read/write operations in error handlers to recover gracefully from missing, corrupted JSON, or storage quota errors. | Injecting HTML tags in complaint titles or notes renders harmless escaped text; corrupted JSON in `LocalStorage` automatically recovers to valid default demo data without crashing the UI. |
| **NFR2** | **Usability, Responsiveness & Accessibility** | The interface shall implement a consistent dark-navy SaaS layout with blue/cyan accents, desktop sidebar navigation, responsive mobile drawer navigation, clear status/priority visual indicators, descriptive empty states, toast notifications, semantic labels, and visible keyboard focus outlines. | Layout adapts cleanly across desktop (`1440px`), tablet, and mobile (`375px`) viewports without horizontal page overflow; every interactive button performs a verified action; modals support `Escape` key dismissal. |
| **NFR3** | **Zero-Dependency Prototype Portability** | The web application shall run directly in modern browsers using only HTML5, CSS3, and Vanilla JavaScript without paid services, backend servers, build tools, or runtime frameworks, remaining fully operational even if optional external Google Fonts fail to load offline. | Opening `index.html` directly or over a static local server loads the complete functional prototype with zero console errors and zero external runtime failures. |
